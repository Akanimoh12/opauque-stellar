> `multisig` field is `null`, and `attestation-engine-v2`, `privacy-pool`,

> automation can execute — see "Why this isn't automated" below.

## Why this isn't automated

The mechanism this migrates to (`contracts/multisig-admin` — see
[`MULTISIG_ADMIN.md`](MULTISIG_ADMIN.md)) is fully built and tested. What
remains is running `scripts/migrate-to-multisig-admin.ts` against the live
testnet deployment, which:

1. Deploys a new contract to the live network (an on-chain, fee-costing
   transaction).
2. Calls `transfer_admin` on four already-deployed, in-use contracts —
   **immediately and irreversibly** removing the current single deployer
   key's admin access on each, per that function's own documented behavior.
3. Requires the actual `STELLAR_DEPLOYER_SECRET` (or a configured
   `stellar-cli` identity) for whoever currently holds admin on those four
   contracts, and the real public keys of every proposed multisig signer.

None of those inputs exist in, or should ever be generated by, an automated
contribution workflow. This runbook — plus the ready-to-run script referenced
below — is the actionable deliverable an operator with those keys executes.

## Prerequisites

- [ ] `stellar-cli` installed and configured (`.stellar-version` pins the
      version this repo tests against).
- [ ] The account currently holding admin on all four registries (or its
      secret) is available as `STELLAR_DEPLOYER` (identity name, preferred)
      or `STELLAR_DEPLOYER_SECRET` in `.env` — see `.env.example`.
- [ ] The account is funded with enough testnet XLM for one contract deploy
      and up to 5 invocations (deploy + initialize + up to 5 transfer calls,
      since `attestation-engine-v2` needs two).
- [ ] `npm run deploy:testnet -- --dry-run` (or an equivalent recent
      successful build) confirms the workspace builds cleanly, so
      `stellar contract build` inside the migration script won't surprise you.

## Step 1 — Select signers and threshold

This is a decision for the team, not a technical default. Record the
rationale here (or link to wherever it's recorded) before running anything:

- **Signers:** who holds each key, and how (hardware wallet, dedicated
  signing machine, etc.)? For a testnet migration, a smaller set (e.g. 3) is
  reasonable; production/mainnet should use however many independent
  keyholders the team's actual operational security model calls for.
- **Threshold:** `initialize` rejects fewer than 2 signers or a threshold
  below 2 (see `MULTISIG_ADMIN.md`) — a 1-of-1 "multisig" satisfies none of
  the security goals this migration exists for. A common starting point is
  2-of-3, raised as the signer set grows.
- Confirm every signer's G-address independently (not just copy-pasted from
  one shared doc) before proceeding — a typo'd signer address in
  `initialize` means that "signer" can never actually approve anything, and
  the multisig would need a full signer rotation (or redeployment, pre-launch)
  to fix.

Record the chosen signers/threshold and the reasoning:

```
Signers (testnet):
  1. <name/role> — G...
  2. <name/role> — G...
  3. <name/role> — G...
Threshold: 2 of 3
Rationale: <why this threshold — e.g. "tolerates one signer being
  unavailable/compromised without blocking legitimate operations">
```

## Step 2 — Dry run

Always dry-run first. This builds the contracts and prints every planned
call without submitting any transaction or touching the manifest:

```bash
node scripts/migrate-to-multisig-admin.ts --network testnet --dry-run \
  --signers G...,G...,G... \
  --threshold 2
```

Review the printed plan against Step 1's decision before proceeding. Confirm:

- [ ] The signer list and threshold printed match what was decided.
- [ ] The four target registries and their contract IDs printed match
      `deployments/v1/testnet.json`'s current `contracts`/`wiring` entries.

## Step 3 — Run the migration

```bash
node scripts/migrate-to-multisig-admin.ts --network testnet \
  --signers G...,G...,G... \
  --threshold 2
```

This deploys `multisig-admin`, calls `initialize`, verifies the on-chain
config via `get_config()` matches what was requested, then calls
`transfer_admin` (and, for `attestation-engine-v2`, `transfer_governance`)
on each of the four registries in turn, verifying and logging each one.

**If any individual registry's transfer fails partway through:** the script
stops migrating *that* registry, records what succeeded in the manifest, and
exits non-zero listing exactly which registries were and weren't migrated.
Re-run with `--only <registryName> --skip-build` (reusing the same
already-deployed multisig address is not currently automated by this script
for a partial retry — see "Partial-failure recovery" below) once the
underlying issue is fixed.

### Partial-failure recovery

The script deliberately refuses to re-run once `deployments/v1/testnet.json`
already records a deployed multisig (`manifest.multisig.address` is set) —
see the script's own guard. If a partial failure leaves some registries
un-migrated after the multisig is already deployed and initialized:

1. Do **not** re-run the full script (it will refuse, and re-deploying a
   second `multisig-admin` when one already exists would fragment admin
   control across two multisig contracts).
2. Manually call the specific failed registry's `transfer_admin` (and
   `transfer_governance` for `attestation-engine-v2`) via `stellar contract
   invoke`, using the multisig address already recorded in
   `manifest.multisig.address`.
3. Manually update `deployments/v1/testnet.json`'s `wiring.<registry>.admin`
   (and `.governance` if applicable) and `multisig.migratedRegistries` to
   reflect the completed state.

## Step 4 — Verify

For each migrated registry, confirm on-chain state matches the manifest:

```bash
stellar contract invoke --id <registryContractId> --network testnet -- get_config
# admin (and governance, for attestation-engine-v2) should now read the
# multisig-admin contract's address, not the old deployer G-address.
```

And confirm the multisig itself:

```bash
stellar contract invoke --id <multisigAddress> --network testnet -- get_config
# signers should list exactly the addresses from Step 1; threshold should match.
```

## Step 5 — Exercise the propose/approve path once, for real

Before considering the migration "operationally complete," have two
different signers actually propose and approve one real admin action through
the multisig (e.g. `relayer-registry`'s `set_config` with an unchanged value,
or another low-risk no-op-equivalent call) — see `MULTISIG_ADMIN.md`
"Publishing a registry admin call" for the exact `propose_call`/`approve`
shape. This confirms the signers' actual key material works end-to-end
against the live deployment, not just that `get_config()` reports the right
addresses.

## Mainnet

This runbook is written for testnet. Before repeating it against mainnet:
review [`SECURITY.md`](../SECURITY.md)'s mainnet audit-signoff gate (the
same one `scripts/deploy-contracts.ts` enforces for new deployments) — a
mainnet admin-authority change is exactly the kind of action that gate
exists for, even though this script does not currently invoke that check
itself (it inherits `scripts/deploy-contracts.ts`'s build step but not its
`verify-security-audit.ts` gate — file a follow-up if mainnet migration is
being planned, so that gate is added to this script too before it's used
there).
